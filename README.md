# 🛡️ Shieldgate

**A free, open-source security gate for pull requests.** Shieldgate runs four open-source
scanners and posts **one** readable PR comment that it edits in place on each re-run:

* **SAST:** Semgrep with Shieldgate's **own 36-rule pack** for Python, JS/TS and Java. Every
  rule maps to CWE and OWASP Top 10, includes a fix hint, and has a test fixture.
* **Secrets:** Gitleaks with a tuned config and an entropy gate. Secret values are masked in
  every output.
* **Dependencies:** OSV-Scanner reports known CVEs with the version that fixes them.
* **IaC and containers:** Checkov covers Dockerfiles, Kubernetes YAML and Terraform.

Findings go through one pipeline: normalize → dedupe → diff-scope → baseline. The results are
then rendered three ways: the PR comment, SARIF for GitHub's **Security** tab, and a configurable
fail threshold. Shieldgate costs **$0**: it runs on GitHub-hosted runners (free for public
repos) and uses no paid APIs or SaaS tokens.

```
PR opened ──► semgrep (custom rules) ─┐
              gitleaks (masked)      ─┤   normalize → dedupe → changed lines only
              osv-scanner (CVEs)     ─┼─► → baseline suppressions → severity gate
              checkov (IaC)          ─┘        │
                                               ├─► single sticky PR comment
                                               ├─► SARIF → Security tab
                                               └─► ✅ / ❌ check
```

## Quickstart

Create `.github/workflows/shieldgate.yml`:

```yaml
name: Shieldgate
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read          # check out the code
  pull-requests: write    # create/update the single Shieldgate comment
  security-events: write  # upload SARIF to the Security tab

jobs:
  shieldgate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # lets PR scans diff against the merge base
      - uses: abidranesh/SHIELDGATE@v1
        with:
          fail-on: high    # critical | high | medium | low | info | none
```

On `pull_request`, Shieldgate reports only findings on **lines the PR changed**, plus CVEs in
dependency manifests the PR touched. On `push` to `main`, it scans the full repository.

### Inputs

| Input | Default | Description |
|---|---|---|
| `fail-on` | `high` | Fail the check when a finding is at or above this severity (`none` = report only) |
| `scope` | `auto` | `auto` (diff on PRs, full otherwise), `diff`, or `full` |
| `scanners` | `semgrep,gitleaks,osv,checkov` | Run a subset |
| `path` | `.` | Directory to scan |
| `exclude` | | Newline-separated globs to ignore, e.g. `tests/fixtures/*` |
| `baseline` | `.shieldgate-baseline.yml` | Suppression file (see below) |
| `extra-rules` | | Extra Semgrep config, added to the bundled pack |
| `comment` | `true` | Post/update the PR comment |
| `upload-sarif` | `true` | Upload SARIF to code scanning |
| `token` | `github.token` | Token used for the PR comment |

Outputs: `findings`, `sarif-file`, `exit-code`.

### Permissions (least privilege)

| Permission | Why | If missing |
|---|---|---|
| `contents: read` | checkout | required |
| `pull-requests: write` | create or edit **one** comment, found by a hidden marker | comment is skipped with a log line; results still go to the job summary |
| `security-events: write` | SARIF upload | upload step is skipped (`continue-on-error`) |

Shieldgate needs no other scopes and no secrets. PRs from forks get a read-only token, so the
comment and SARIF upload are skipped there. The job summary and the pass/fail check still work.

## Baseline: accepting findings on purpose

```yaml
# .shieldgate-baseline.yml
suppressions:
  - fingerprint: 3f2a9c0d1e2b4a5f          # one specific finding (shown in SARIF / --json)
    reason: "Test fixture, never deployed"
  - rule_id: shieldgate.python.weak-password-hash
    path: "legacy/*"
    reason: "Legacy MD5 cache keys, not passwords. Ticket SEC-142"
    expires: 2027-03-31                     # forces a re-review
```

* Every entry **must** have a `reason`. Without one the scan fails with a configuration error
  (exit 2).
* Fingerprints hash the rule, file and normalized code snippet (for dependencies: the package
  and version). Line numbers are not part of the hash, so a suppression survives code moving
  up or down the file.
* `shieldgate baseline -o .shieldgate-baseline.yml` writes the current findings as a starting
  baseline when you first adopt the tool. Edit each reason before committing it.

## Shieldgate vs. running the tools separately

| | 4 separate actions/tools | Shieldgate |
|---|---|---|
| PR feedback | up to 4 bot comments/annotations in 4 formats, or none | **1** comment, edited in place on re-runs |
| Scope on PRs | mostly whole-repo, so old debt shows up on every PR | **changed lines only** (full scan on `main`) |
| Duplicates | Gitleaks and a Semgrep secret rule both report the same line | merged into one finding, CWE/OWASP mappings combined |
| Severity | 4 different scales (ERROR/WARNING, CVSS, none for Checkov OSS) | one 5-level scale, one `fail-on` gate |
| Accepting risk | 4 ignore mechanisms (`nosemgrep`, `.gitleaksignore`, `--skip-check`, OSV config) | one baseline file with mandatory reasons and expiry |
| Secrets in logs | depends on flags | always masked (`ghp_****…`); the secret line is never echoed |
| Fix guidance | generic per tool | per-rule fix hint; minimum safe version per package |
| Custom rules | write your own | 36 CWE/OWASP-mapped rules with tests, benchmarked |
| Cost | free | free |

Measured on the demo PR: the four tools produce 39 raw findings on the vulnerable commit.
Shieldgate reports 38. Gitleaks' built-in `generic-api-key` rule and Shieldgate's entropy rule
both flag the planted key, and the duplicate is merged.

## Run locally

```bash
pip install -e . semgrep==1.183.0 checkov==3.2.300
# install gitleaks 8.21.2 and osv-scanner 1.9.2 binaries from their GitHub releases
shieldgate scan .                          # full scan, fail on high+
shieldgate scan . --diff-base origin/main  # only what your branch changed
shieldgate scan . --sarif out.sarif --json out.json --markdown comment.md --fail-on none
SHIELDGATE_OSV_OFFLINE=1 shieldgate scan .  # OSV via downloaded DB instead of api.osv.dev
```

Exit codes: `0` pass, `1` findings at/above `--fail-on`, `2` configuration error (e.g. a
baseline entry without a reason). A missing scanner binary is skipped with a warning unless
you pass `--strict`.

## Engineering notes

* **Pinned tools:** Semgrep 1.183.0 and Checkov 3.2.300 (pip, each in its own venv);
  Gitleaks 8.21.2 and OSV-Scanner 1.9.2 (release binaries, **SHA-256 verified** in
  `action.yml`). First-party actions (`actions/setup-python@v5`,
  `github/codeql-action/upload-sarif@v3`) are pinned by major tag. Pin them to commit SHAs if
  your policy requires it.
* **CI** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)): pytest, `semgrep --validate`,
  `semgrep --test`, rule metadata lint.
  **Self-scan** ([`self-scan.yml`](.github/workflows/self-scan.yml)): Shieldgate scans its own
  repo, excluding the deliberately vulnerable fixtures.
* **Scope:** Shieldgate ships detection rules and scanner orchestration only. Vulnerable code
  exists only as clearly labeled test fixtures (`rules/**`, `demo-vulnerable-app/pr-steps/1-vulnerable`).

## Publishing to the GitHub Marketplace (manual steps)

1. Make sure the repo is **public** and that `action.yml` is at the root with a unique `name`,
   plus `description` and `branding`. All three are already set.
2. Accept the GitHub Marketplace Developer Agreement (prompted on first publish). Enable 2FA on
   your account.
3. Push to `main`, then create a release: **Releases → Draft a new release → tag `v1.0.0`**. Tick
   **"Publish this Action to the GitHub Marketplace"** and choose the categories *Security* and
   *Code quality*. If the name `Shieldgate Security Scan` is taken, rename it in `action.yml`.
4. Add a moving major tag so users can write `@v1`:
   ```bash
   git tag -fa v1 -m "v1" && git push origin v1 --force
   ```
   Move `v1` forward on every compatible release.
5. Open the demo PR (`demo-vulnerable-app/make-demo-pr.sh`), take the three screenshots, and
   commit them to `docs/img/`.
